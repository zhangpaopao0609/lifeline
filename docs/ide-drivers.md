# IDE Drivers (pluggable IDE adapters on the agent)

**English** | [简体中文](./zh-CN/ide-drivers.md)

## Topology

```
index.ts (walks registeredDrivers() and wires them)
  └─ createIdeSlot(kind)            ← skeleton only: lookup DRIVERS[kind], one lifecycle
       ├─ driver.bridgeOptions()     CDP bridge diffs (titleSuffixes/appNames/relauncher)
       ├─ driver.createExtractor()   DOMExtractor | CodeBuddyExtractor
       ├─ driver.createExecutor()    CommandExecutor | CodeBuddyExecutor
       ├─ driver.attachLive(handle)  how live state attaches after connect (the deepest split)
       └─ WindowMonitor              kind + driver.windowMonitor (declarative diffs)
```

**One driver = all wiring for one IDE**: `cdpUrlOf` (config field map), `portCandidates` (DevToolsActivePort discovery), `argvPaths` (CLI writes argv.json), `hasLiveApp` (probe — **quiet policy only, never a gate**), `openDiskAdapter` (on-disk session source: cursor SQLite / codebuddy JSON), `capabilities` (command matrix, e.g. `getPlanFull`).

## Design decisions (do not overturn these)

1. **Live-attach policy lives entirely on the driver, not as hook callbacks.** CodeBuddy is dual-connection: besides workbench CDP, live state uses a direct `CdpClient` to the coding-copilot webview, with generation (`liveGen`) and `nextReconnectDelay` backoff (engine in `cdp/relaunch-engine.ts`). Leave that state machine in the slot and `kind ===` forks grow back, so the whole block moved into `drivers/codebuddy/driver.ts`. Cursor `attachLive` is three lines (hang the workbench client).
2. **Per-slot state is a WeakMap.** The driver is a singleton; live state (gen / retry / client) on the driver instance would leak across slots — `codebuddy/driver.ts` keeps `liveStates = new WeakMap<LiveSlotHandle, LiveState>()`. Tests can build several same-kind slots without crosstalk.
3. **The driver drives live state through the `LiveSlotHandle` surface**, not slot-private fields. The surface (cdp / stateManager / extractor / executor / currentCdpUrl / test hooks) is built when `createIdeSlot` assembles; `CreateIdeSlotOptions` test hooks pass through as-is.
4. **window-monitor only lifts declarative diffs.** wsUrl filtering (`otherWindowsRequireWsUrl`) is on the driver; `pollWindowParallel` dispatch and `extractFromClient` guards stay inside the monitor (`pollCodeBuddyWindow` is bound to monitor-private state; lifting it explodes the interface; a new IDE needs a new window poll anyway).
5. **`connection:status` is per-IDE.** The agent reports per driver (payload includes `ide`); server `applyConnection` writes the matching slot. Old agents (≤0.1.72) without `ide` fall back to the cursor slot. The old `reportsConnectionStatus` quirk (cursor only) is gone.

## Checklist for a new IDE

1. `packages/protocol/src/wire.ts`: add one `IDE_KINDS` entry (types / zod / labels / lists all fan out)
2. `packages/agent/src/drivers/<kind>/`: one directory for that IDE — `driver.ts` (probe, ports, argv, disk source, capabilities) + `extractor.ts` / `executor.ts` / `live.ts` / `relaunch.ts` as needed (**the IDE's own diffs cannot be avoided**; mirror `cursor/` and `codebuddy/`)
3. `drivers/index.ts`: register
4. `window-monitor.ts`: window poll for that IDE (see decision 4)
5. CLI argv ensure/remove if that IDE needs it (table-driven at the function layer)
6. Zero server changes (`Partial<Record<IdeKind, …>>` already fans out)

## Pitfalls (criteria)

- **Cursor subagents are saved composers.** `task_v2.result.agentId` is the child composer id. Before that result is written, match the parent's `subagentComposerIds` against each child's `subagentInfo.parentComposerId` and `toolCallId` / `toolCallIdHistory`. Association changes must invalidate the projection even if the task bubble is unchanged. Reading a child follows it alongside the active/root session; it must not take over that session's follow target, including on content-only machines.
- **Runtime callback signatures include an `ide` parameter.** `ContentLiveRuntime` onSessionFull/Append/Patch/Sync is `(sessionId, messages, ide, seq)` — the runtime passes `adapter.ide`. Do not shadow it with an outer loop variable (equivalent, but missing the parameter fails TS).
- **`ContentSource.close()` is optional:** call `adapter.close?.()`.
- **`CursorWindow['kind']` is optional** (`kind?`): the driver interface types windowKind as `WindowKind`; callers `?? 'project'`.
- **Never self-heal while the IDE updater (ShipIt) is resident**（实测 2026-10-10，Cursor 3.23→3.24 ToDesktop/Squirrel.Mac）：用户点「重启并更新」后 ShipIt 常驻等应用退出，替换整个 `.app` 需 8–15s；这期间 agent 的自愈 `open -a Cursor` 会把**旧包**拉回来，ShipIt 以 "App Still Running" 中止，更新永远装不上（用户反馈：升 3.24.9/3.24.12 反复失败）。所以 `relaunch-engine.ts` 在 quit 之前先问 `isUpdaterRunning()`（macOS `pgrep -f '<App>.app/…/Squirrel.framework/Resources/ShipIt'`）→ 返回 `skipped-update-in-progress`，安静轮询等 ShipIt 自己起新版本（bridge 按 `skipped-not-running` 同样处理）。该跳过**不消耗 cooldown / burst**，理由同 `skipped-no-exe`。
- **静默期的唤醒只许用进程探针（pgrep/tasklist），不许把 CDP 轮询调快**：每轮重连一条 `Reconnecting in …` 日志，快速档 = 每分钟十余行/IDE 的永久噪声（`noExeLogged` 存在的理由）；且 no-listener 之外的探测分支还要跑 `lsof`。上升沿唤醒（`QuietWake`，bridge 静默档才武装，基线在 arm 时采样）+ 30s CDP 兜底是刻意结构，见 `cdp/bridge.ts`。冷却只保护真动作：quit 成功才记 `lastAttempt`（open 失败仍吃冷却——"杀了没拉起"绝不能快轮询重试），quit 失败走 15s 短门（`QUIT_PENDING_RETRY_MS`，锚在 quit **返回**时——一次失败本身就要 25–35s）；`skipped-throttled` 与 `skipped-quit-pending` 也归安静档，否则保险丝触发后 500ms 风暴刷满 10 分钟窗口、保存弹窗卡住期间 500ms 风暴无上界。
- **Extractor callback `errorMessage` is `string | null | undefined`:** factory context types must match.
- **Cursor's Agents Window moved the message headers into `composerConvHeaders` chunks** (measured 2026-10-31 on Windows Cursor; `state.vscdb` = `ItemTable` / `composerHeaders` / `cursorDiskKV`): for new chats `composerData.fullConversationHeadersOnly` is an **empty array** and `conversationMap` an empty object; the headers live in `cursorDiskKV` rows `composerConvHeaders:<composerId>:<six-digit chunk>` (256 entries per chunk), pointed at by `composerData.headerLog {chunkSize, chunkCount, count, generation}`. Bubble bodies keep the old key `bubbleId:<sid>:<bid>`, and a chunked header's `bubbleId` already carries the `/s:N` suffix — it *is* the body key tail. Old chats still carry the inline array, and **both forms are `_v: 18`**, so name the format by `headerLog`, never by schema version. Reading the inline array alone lists the chat but projects an empty body. `readHeaders()` in `cursor-adapter.ts` is the single entry point (trims stale tail chunks with `chunkCount`, falls back to the inline array while chunks are not written yet).
- **CodeBuddy 单选问卷的选项要点两次**（CDP 实测 2026-10-05，CodeBuddy CN 1.106.1）：IDE 自己的 `question-floating.react` 里选项 `onClick` = `onOptionSelect(v); setTimeout(() => onSubmit(), 0)`，而那个 `onSubmit` 闭包读的是**上一次**的 `selectedAnswer` —— 第一次点击只画上 `selected_`、不提交；第二次点击才提交，且提交的是**上一次**选中的那个（先点 A 再点 B，落到线上的是 A）。所以 `..._optionItem_`（single mode）必须走 `codebuddySingleOptionClickExpression`：点 → 等 `selected_` 落在这行 → 再点同一行（`selected_` 已存在时只点一次，那一下就是提交）；overlay 已经不在（答完/被关/折叠）时返回 ok 而不是 `Element not found`，否则「确认」那 ~1s 里再点另一个选项会给已答完的问卷弹报错。`..._option_`（multi mode，含多选）是 toggle 语义，必须保持一次点击 —— 双击会把刚选上的选项取消掉。**残留**：若用户在 IDE 里先手动点了一行（IDE 状态里持有一个未提交的答案），再在 Lifeline 上点**别的**选项，IDE 会在点击那一刻提交它自己持有的那个旧答案（`via: 'single-submitted'`）——这是 IDE 侧行为，agent 无法阻止。
- **Composer attachments travel in `command:send_message`, not through an upload endpoint.** Bytes are base64 in the payload; the agent writes them under `~/.lifeline/uploads` and then either pastes them into the IDE (native) or types their local paths (fallback). `commandPayloadSchema` is a plain `z.object`, so an old server or agent **strips** `attachments` while the text still goes through — the message arrives, the files vanish. All three sides move together.
- **A paste targets whichever composer is in front, so `landOnOpenChat` must run before `materializeAttachments`** (`command-router.ts`): otherwise the file lands in the previous session and the words in this one. Native-paste success is judged by the composer's attachment-node count **growing** — never by `preventDefault`, because an editor may swallow a paste it does not keep. Partial acceptance (2 of 4 files) counts as failure: the router types the paths instead, since a chip the model never sees is worse than a path it can read. Do not lower the bar to "the IDE did not error".
- **`preserveComposer` means the editor already holds a native attachment.** Do not select-all + retype: `codebuddy/executor.ts` skips the insert when the text is empty and `cursor/executor.ts` keeps the chip node. Re-inserting deletes the attachment, and the message goes out with the words but without the file.
- **Cursor 侧边栏「运行中」图标是 glass 点阵 loader**（CDP 实测 2026-10-10，Cursor 3.24.9）：运行中的会话行，前导图标是 `.agent-sidebar-cell-icon .ui-dot-grid-loader[data-shape="sine_3x3"]`（与 Agents 窗口的行同一个组件）；**旧 `.spinning-loader` / `.cursor-icon-modifier-spin` 在项目窗口里已不再出现**。`cursor/extractor.ts` 的 `cellIsRunning` 漏掉它就报 `active`，而 web 侧「行状态优先于窗口级 live」（`hasRowStatus`）→ 顶部写"空闲"、composer 不锁（用户反馈：会话明明在跑）。判定必须限定在 `.agent-sidebar-cell-icon` 槽位内：已完成行那里是 `.ui-agent-status-dot[data-variant=done-seen]`，不要把它当 running。
- **CodeBuddy also runs as a VSCode plugin, and every VSCode-aware behavior is plugin-gated** (measured 2026-11-03, VSCode + `tencent-cloud.coding-copilot`): the coding-copilot panel is an extension webview, so the same `codebuddy` IDE kind covers both hosts — same webview DOM (extractor/executor unchanged), same history root `CodeBuddyExtension/Data` (the plugin writes `<uid>/VSCode/`, the IDE `<uid>/CodeBuddyIDE/`; the adapter scans both). **End-to-end verified 2026-11-04** against a live VSCode 1.144.1 (temp `--user-data-dir` instance): the plugin webview's CDP target URL is `vscode-webview://<hash>/index.html?...&extensionId=Tencent-Cloud.coding-copilot&...` — plain VSCode encodes the extension id in the query (the CodeBuddy IDE fork names the origin directly), and **both shapes contain the lowercase `coding-copilot` substring**, so `pickCodingCopilotTarget`'s filter needs no change; the real `dumpCodeBuddyLive` on that webview returns Craft/Auto mode-model fields (DOM identical). Also measured: `open -a "Visual Studio Code" --args --remote-debugging-port=N` is a **no-op when an instance is already running** (single-instance forwarding drops the flag — the new process prints `DevTools listening` then exits), which is exactly why the relauncher must quit first. What differs is launch/paths, and the gate is `vscodeCodeBuddyPluginInstalled()` (`~/.vscode/extensions/tencent-cloud.coding-copilot*`): **ungated it would write argv ports into — and self-heal-restart — every plain-VSCode machine** (VSCode is near-universal; CodeBuddy IDE is not). Rules: ① VSCode joins `isRunning`/quit/open (the "family") only through the gate; ② quit must remember which product it closed and reopen **that one** (quitting plugin-VSCode and reopening CodeBuddy is worse than no self-heal), and it must be **single-target** on both platforms — a running CodeBuddy image wins, otherwise only `Code.exe` (`pickCodeBuddyQuitImagesWin` on Windows). ⚠️ "what we kill" and "what we wait for" must be the same set: `quitProcessWin`'s default derives the poll from the images it killed; passing an independent family predicate made `taskkill` hit CodeBuddy only while a live `Code.exe` held the poll true → `skipped-quit-pending` → Windows plugin machines never self-healed; ③ port/argv candidate lists stay **pure** — the driver passes the gate explicitly, functions default to "no VSCode", so tests stay machine-independent (a default-IO gate once made `codeBuddyArgvCandidates` return 7 entries on dev machines and 6 on CI); ④ VSCode reads argv.json from `~/.vscode/argv.json` on **all** platforms — NOT userDataDir like Cursor/CodeBuddy; `removeCodeBuddyCdpArgv` always includes it (a machine may lose the plugin before uninstall); ⚠️ **write one file per installed host, never "first installed product wins"** (`resolveCodeBuddyArgvPaths`): that rule only holds for CN vs international (mutually exclusive), while VSCode is a *second, simultaneously usable* host — writing only the standalone IDE's file leaves a self-started VSCode without a debug port, so the relauncher quits and reopens it every time. On **Linux** this file is still written although the agent never controls an IDE there (content source only) — pre-existing for Cursor / the CodeBuddy IDE, now extended to the VSCode file; kept as-is so uninstall stays symmetric, and it becomes meaningful again with `LIFELINE_LINUX_CDP=1`; ⑤ probe (`probe.ts`) treats a VSCode workbench/UA as "unknown, accept" for `codebuddy` (it is a family member) and foreign only for `cursor`; ⑥ VSCode's window title separator is an em dash on macOS (` — Visual Studio Code`) — both dash flavors are in `CODEBUDDY_TITLE_SUFFIXES`; ⑦ **`host` is display metadata, learned from the endpoint, never from install inventory**: `hostOf` (probe) reads the workbench app path, falling back to the UA (` Code/<n>`); absent = unknown → the console shows the plain product name. Never default it to `ide`: a plugin-only machine would be told to open an app it does not have. Status copy names **VS Code** for the plugin host (`ideSubject`), because that is the process we quit and reopen. ⑧ Port discovery walks **past files nobody answers**, never past one that answers: a host that crashes (rather than exiting cleanly) leaves its `DevToolsActivePort` behind, and each host has its own file — stopping at the first readable candidate made a dual-install machine unable to reach the live one, so VSCode got quit+reopened on every cold start. Keep `no-listener` as the **only** reason to continue (anything that answers is adopted — that is review R3), and keep the returned `fileMtime` **and the endpoint-cache key** on the **adopted** file: `cdp-bridge` judges "did this file move after the relaunch" from it, and the first candidate may be the other host's leftover. ⑨ **Never trust `pgrep` alone for "is the app running" on macOS**: measured 2026-11-05, CodeBuddy CN's main process was invisible to `pgrep` under every pattern (`-f "<App>.app/Contents/MacOS/"`, `-f CodeBuddy`, even `-x Electron`) while `ps -axo pid=,command=` listed it — same user/session, both Dock and `open --args` launches, while WorkBuddy's `Electron` processes *were* visible. Consequence: `isCodeBuddyRunning` said "not running" for a running IDE, the family predicate was satisfied by VSCode, and the relauncher **quit VSCode** instead of the standalone IDE that had no port. `isDarwinProcessRunning` therefore falls back to `ps` (one snapshot per 5s, shared by every pattern). Windows needs no equivalent: `tasklist` matches exact image names and has no argv dependency.
